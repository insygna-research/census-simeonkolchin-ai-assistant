# Roadmap: новые возможности Team Assistant

Документ описывает фичи, которые хотим добавить, с оценкой реализуемости и привязкой
к текущей архитектуре (FastAPI + litellm + A2A, тулы регистрируются в
`src/agent/team_agent.py`, интеграции — в `src/tools/`, персистентность — в `src/storage/`).

Статус на момент написания:
- Мульти-сервер паттерн уже есть у **YouGile** (`MultiYouGileTool`) и **Outline** (`MultiOutlineTool`).
- **Планировщика/фоновых задач нет** (в `requirements.txt` нет apscheduler/cron).
- Проактивные сообщения можно слать через готовый `telegram send_message`.

---

## 1. Планировщик тренировок + автономный агент

### Что хотим
- Составлять и хранить план тренировок.
- Автономный агент сам, по расписанию, спрашивает «как прошла тренировка?», собирает
  ответы, ведёт историю, корректирует план.

### Чего сейчас не хватает
1. **Планировщик фоновых задач.** Сейчас агент работает только реактивно (запрос →
   ответ через UI/A2A). Нужен компонент, который сам инициирует действия по времени.
2. **Проактивный канал общения.** Готов `telegram send_message` — можно использовать
   как способ «постучаться» пользователю.
3. **Хранилище тренировок.** Своя таблица (по образцу `src/storage/chat_db.py`, SQLite).

### Предлагаемая реализация
- Добавить зависимость `APScheduler` (AsyncIOScheduler), поднимать её в `src/app.py`
  на старте FastAPI (lifespan).
- Новый модуль `src/tools/training_tool.py`:
  - `create_plan`, `get_plan`, `update_plan`
  - `log_workout` (факт + ощущения/нагрузка), `get_history`, `get_stats`
- Новое хранилище `src/storage/training_db.py` (SQLite): планы, запланированные
  тренировки, факт выполнения.
- Новый модуль `src/agent/scheduler.py`:
  - джоба «напомнить о тренировке» и джоба «спросить как прошло» (через N часов после
    запланированного времени);
  - когда пользователь не ответил — повторный мягкий пинг.
- Диалог «как прошло» ведёт LLM: получает контекст из `training_db`, задаёт вопрос в
  Telegram, парсит ответ, вызывает `log_workout`.

### Оценка
Средняя. Основная новая инфраструктура — планировщик + проактивные диалоги
(этого в проекте ещё нет). Остальное — по существующим паттернам.

## 2. Календарь iCloud

### Что хотим
Смотреть события и добавлять их в календарь iCloud.

### Реализуемость — да, через CalDAV
У Apple нет публичного REST API для календаря, но iCloud поддерживает **CalDAV**
(`caldav.icloud.com`). Аутентификация — Apple ID + **app-specific password**
(обычный пароль не подойдёт, 2FA обязательна).

### Предлагаемая реализация
- Зависимость: `caldav` (Python-библиотека) или `icalendar` + httpx.
- Новый модуль `src/tools/icloud_calendar_tool.py`:
  - `list_calendars`
  - `list_events(calendar, date_from, date_to)`
  - `create_event(calendar, title, start, end, notes, location)`
  - `update_event`, `delete_event`
- Конфиг: `ICLOUD_USERNAME`, `ICLOUD_APP_PASSWORD` в `.env` / `src/config.py`.

### Риски / нюансы
- App-specific password нужно создавать вручную в appleid.apple.com.
- CalDAV бывает капризным (таймзоны, RRULE для повторов) — начать с простых событий.
- Хорошо ложится на фичу №1: агент тренировок может сразу класть тренировки в календарь.

### Оценка
Средняя. Библиотека готовая, основная возня — auth и таймзоны/повторы.

## 3. Несколько GitLab (разные URL / авторизации)

### Что хотим
Подключить несколько GitLab-инстансов с разными токенами и URL.

### Текущее состояние
`GitLabTool` уже принимает `url` + `token` в конструкторе — то есть на уровне класса
мультиинстанс возможен. **Но** конфиг хранит только один `GITLAB_URL/GITLAB_TOKEN`,
и в `team_agent.py` создаётся один инстанс. У YouGile и Outline уже есть
`Multi*Tool` — берём тот же паттерн.

### Предлагаемая реализация
- Новый класс `MultiGitLabTool` (по образцу `MultiYouGileTool`), который держит список
  инстансов и роутит вызовы по параметру `instance` (или имени сервера).
- Конфиг — список серверов. Варианты:
  - JSON в одной переменной `GITLAB_SERVERS='[{"name":...,"url":...,"token":...}]'`, **или**
  - хранилище по образцу `src/storage/yougile_tokens.py` + управление через UI.
- В `GITLAB_TOOLS` дефинишены добавить необязательный аргумент `instance`; если не
  указан — использовать дефолтный/спросить.

### Оценка
Низкая. Есть два готовых образца (`MultiYouGileTool`, `MultiOutlineTool`) —
по сути повторение.

## 4. Интеграция с Obsidian

### Что хотим
Читать/писать заметки в Obsidian-хранилище (vault).

### Ключевой вопрос — как получать доступ к vault
Obsidian — это локальное приложение поверх папки с `.md` файлами. Варианты доступа:

1. **Файловый доступ к vault (проще всего).** Если папка vault доступна серверу/агенту
   (примонтирована, синхронизирована), работаем напрямую с `.md`:
   - `search_notes`, `read_note`, `create_note`, `append_to_note`, `update_note`
   - парсинг frontmatter (YAML), `[[wikilinks]]`, тегов.
   - Плюс: не нужен сам Obsidian запущенным. Минус: нет «живой» синхронизации, если
     vault только на устройстве пользователя.
2. **Obsidian Local REST API (плагин).** Community-плагин поднимает HTTP API на
   машине с Obsidian. Плюс: работает с «живым» vault. Минус: Obsidian должен быть
   запущен, API локальный (нужен туннель/сеть до сервера).
3. **Через синхронизацию файлов** (iCloud/Git-vault): агент работает с git-репозиторием
   vault — тогда это фактически вариант 1 + `git pull/push`.

### Рекомендация
Начать с **варианта 1 (файловый доступ)**, если vault можно синхронизировать в git
или примонтировать. Это переиспользует подход `file_processor.py` и не требует, чтобы
Obsidian был запущен.

### Предлагаемая реализация
- Новый модуль `src/tools/obsidian_tool.py` (файловый доступ к папке vault).
- Конфиг: `OBSIDIAN_VAULT_PATH` (+ опционально git-remote для sync).
- Пересечение с Outline: продумать, где «источник правды» для вики (см. §5).

### Оценка
Низкая–средняя (вариант 1). Средняя, если нужен «живой» доступ через плагин/туннель.

## 5. Вики: Outline или Quartz?

### Короткий ответ
Для нашего кейса (агент **читает и пишет** вики через API, авторизация, поиск) —
**Outline**. Он уже интегрирован (`outline_tool.py`, `MultiOutlineTool`).

### Почему
Это разные классы инструментов:

| Критерий | **Outline** | **Quartz** |
|---|---|---|
| Что это | Полноценное wiki-приложение (сервер + БД) | Генератор статического сайта из markdown/Obsidian |
| API для записи | Да (REST, уже используем) | Нет — только сборка сайта из файлов |
| Редактирование | В вебе, совместное, с правами/поиском | Правишь исходные `.md`, потом ребилд |
| Аутентификация | Да (OIDC/Authentik уже подключён) | Публичный статический сайт (или за прокси) |
| Назначение | Живая база знаний с чтением/записью | **Публикация** заметок как красивого сайта |

### Вывод
- **Outline** — как рабочая вики, куда агент пишет и откуда читает. Оставляем как основу.
- **Quartz** — не конкурент Outline, а дополнение: если хочется **публиковать**
  Obsidian-vault как читаемый сайт. Тогда связка: Obsidian (§4) — источник →
  Quartz — публичная витрина. Но как backend для агента Quartz не подходит (нет API записи).

Рекомендация: **вики оставляем на Outline**; Quartz рассматриваем отдельно и только
если появится задача «опубликовать заметки наружу как сайт».
